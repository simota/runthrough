# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

`runthrough` is an act-style local runner for GitHub Actions workflows, written in Rust (single binary crate). See `README.md` for the user-facing feature list and what is not yet supported.

## Commands

```sh
make check CARGO_FLAGS=--offline          # typecheck + lint (fmt --check, clippy -D warnings) + test
make                                      # list targets: build, test, lint, fmt, typecheck, check, ci
make ci CARGO_FLAGS=--offline             # dogfood: run .github/workflows/build.yml with runthrough --host
cargo test --offline                      # unit tests (in-module) + tests/e2e.rs
cargo test --offline expr::               # unit tests of one module
cargo test --offline --test e2e push_workflow_succeeds   # one e2e test
cargo run -- -C tests/fixtures/repo --host -n   # try the CLI against the fixture repo
```

- `tests/e2e.rs` runs the built binary (through `bin()`, which adds `--no-history`) with `--host --no-cache-server` against `tests/fixtures/repo` (needs `bash`, `node` and `git` on PATH, no Docker). Assertions grep stdout, so changing log/summary line formats (`"<wf> / <job>: <result>"`, the closing `🏁`/`❌ N workflows, M jobs: …` line, masking `***`) can break them.
- The e2e test binary bakes in absolute paths via `CARGO_BIN_EXE_runthrough` / `CARGO_MANIFEST_DIR`. If it fails with `run runthrough: ... NotFound` after the repo directory was moved or renamed, `touch tests/e2e.rs` (or `cargo clean`) to force a rebuild.
- Exit codes: `0` all jobs succeeded/skipped, `1` a job failed, `2` an internal error (`anyhow` error from `run()`).

## Architecture

Pipeline: `main.rs` (CLI + config assembly) → `workflow.rs` (load YAML) → `filters.rs` (`on.<event>` branch/tag/path/type filters) → `planner.rs` (stages, matrix) → `runner.rs` (execute) using `expr.rs`, `actions.rs`, `backend.rs`, `commands.rs`, `matchers.rs`, `context.rs`, `servers.rs`; `info.rs` serves the exit-early modes (`--graph`, `--man-page`, `--list-options`, `--bug-report`, `--install-hook`) and `--watch`'s fingerprint; `history.rs` and `dashboard.rs` record runs and serve `--dashboard`; `markers.rs` formats the job and step status lines the runner logs and `history.rs` parses back.

- **`main.rs`** parses CLI (clap derive; flag names follow act, see `docs/act-parity.md`), discovers workflows (`workflow_paths`: `-W`, or `.github/workflows` plus `.runthrough/workflows`; recursively unless `--no-recurse`), filters by event and its `on.<event>` filters (an explicit `-j` or a single workflow file bypasses both), handles `-l`/`-n`/`-g`/`--validate`, merges `.secrets`/`.vars`/`.env`/`.input` files with CLI flags (flags win), and builds `runner::Config`. Arguments from `.actrc` files are spliced in before the real ones (`actrc_args`). `Cli` is `pub` so `info.rs` and `servers.rs` read it directly.
- **`workflow.rs`** validates every workflow (`schema_errors`: required keys and value types; `strict_check` adds unknown keys under `--strict`), then deserializes it with `serde_yaml`; many fields stay as raw `serde_yaml::Value` because they may contain `${{ }}` and are evaluated later. `yaml_to_json` / `yaml_scalar_to_string` bridge YAML into the JSON values the expression engine uses.
- **`planner.rs`**: `stages()` topologically groups jobs by `needs` (restricted to `-j` plus its transitive needs); `expand_matrix()` handles `include`/`exclude`.
- **`expr.rs`**: self-contained lexer/parser/evaluator for the expression language over `serde_json::Value`. `Ctx` holds all contexts plus `failed`/`cancelled` flags that drive `success()`/`failure()`/`always()`, and `ancestor_unsucceeded` (a job's skipped or cancelled ancestor: `success()` is false while `failure()` is not; `JobRun::ctx_for` clears it for steps). Entry points: `evaluate`, `evaluate_if`, `interpolate` (string), `interpolate_value` (keeps type for a lone `${{ }}`), `interpolate_json`.
- **`runner.rs`** (largest module):
  - `run_workflow` → `run_jobs` runs each stage's jobs in parallel with `std::thread::scope`; `run_job_matrix` fans out matrix legs (filtered by `--matrix`) to `run_job`, or to `run_reusable` for `jobs.<id>.uses`, which calls `run_jobs` on the called workflow with a cloned `Config` (typed inputs, mapped secrets). `Config.shared` (`RunShared`: `Slots`, host claims, concurrency groups, masks, history) is one per invocation; `Config.frame` (`CallFrame`) is per workflow or job leg. `Slots` bounds concurrent `run_job`s (`--concurrent-jobs`); only leaf jobs take a slot, so nested reusable calls cannot deadlock.
  - `JobRun` owns one job's backend, service containers and network, env, PATH additions, post steps, and a per-job root with `workspace/`, `temp/`, `tool/`, `files/` (a tempdir, or a fixed dir under `~/.cache/runthrough/reuse` with `--reuse`). `JobRun::cleanup` removes containers, services and the network.
  - `Concurrency` (in `RunShared`) holds this run's `concurrency` groups; `with_concurrency` wraps a workflow or a job leg and pushes its ticket onto `Config.frame.cancelled_by`, which `JobRun::cancelled` checks.
  - `JobRun::start` resolves the container (`job_container`), starts services (`start_services`) and the job container; everything it creates on the engine is recorded in `JobResources`, which a failed start and `JobRun::cleanup` both `release`.
  - `run_job_steps` runs a job's top-level steps: `background` / `parallel` steps run on scoped threads with a `JobRun::fork` (shared `seq`, own `stop` flag) and are merged back by `finish_background` at `wait` / `wait-all` / `cancel` or the job's end; composite actions go through `run_steps`.
  - `Scope` is per top-level job or per composite action (its own `steps` context, `inputs`, `action_path`); composite actions recurse through `run_steps`.
  - `exec_with` is the single point that spawns step processes: it creates fresh `GITHUB_OUTPUT`/`ENV`/`PATH`/`STATE`/`STEP_SUMMARY` files under `files/<seq>/`, injects env (runner → job → step), parses workflow commands from output, and applies masking. `Target::Backend` runs in the job's backend; `Target::Container` runs a Docker action or `docker://` step as a sibling container started from the host (`run_container_step`), with env passed as `-e`.
  - `Logger` prints through `emit`, which ignores stdout write errors so a closed pipe never skips cleanup.
  - `resolve_platform` maps `runs-on` labels to an image or the host (`-self-hosted` sentinel; `ubuntu*`/`linux` → `DEFAULT_IMAGE`; `self-hosted` and `macos*` on macOS → host).
  - `actions/checkout` is special-cased (`checkout`) unless `--no-skip-checkout`: the own repo is copied (no-op with `--bind`; only the HEAD commit with `--committed`, which also reads the repository's workflows, called ones included, from that commit exported by `actions::export_head` into `Config.committed`), another `repository` is shallow-cloned.
- **`backend.rs`**: `Backend::Host` or `Backend::Container`, driven through a CLI chosen by `Engine` (`docker`, or Apple's `container` via `--engine container`); no container API crate. Engine differences are handled here, as `Engine` methods the runner asks (`quiet_args`, `host_gateway_arg`, `has_network_aliases`, `has_health_checks`, `has_host_network`, `needs_temp_volume`, `is_remote`): Apple `container` gets `--progress none`, has no `--network-alias` (the runner writes service IPs into the job container's `/etc/hosts`) and no health checks (`take_health` strips `--health-*` and `wait_healthy` polls the command with `exec`); `host_address` is `host.docker.internal` for Docker and the network's `ipv4Gateway` for Apple. The job scratch dir is bind-mounted at the **same absolute path** in the container, so host and container paths are interchangeable throughout the runner. Exceptions are the job's volumes (`JobRun.job_volumes`, mounted over those paths): RUNNER_TEMP for Docker jobs, and, where Docker shares host files through a VM (`Engine::shares_files_through_vm`, i.e. Docker Desktop outside Linux) and without `--bind` or the engine socket (whose jobs hand workspace paths to the engine), the workspace; the host does not see writes there, and `sync_in` copies checkouts into it. With a remote Docker (`engine_is_remote`: `DOCKER_HOST=ssh://`/`tcp://`, or `RUNTHROUGH_REMOTE_ENGINE=1` to force it locally) `Config.copy_mode` replaces the mounts with per-job volumes at those same paths; `JobRun::sync_in` and `exec_with` keep them in sync via `docker cp` (temp/ and files/<seq> before each step, files/<seq> back after, checkout results and cached actions once).
- **`actions.rs`**: parses `uses:` (`Local`, `Remote`, `Docker`), loads `action.yml`, and `fetch_remote` git-clones into the action cache (`$XDG_CACHE_HOME/runthrough/actions` or `~/.cache/...`), serialized by a global mutex; `--offline` only uses the cache.
- **`commands.rs`**: parsing of `GITHUB_ENV`-style files (including heredoc delimiters), `::command::` lines, and secret masking.
- **`matchers.rs`**: problem matchers (`::add-matcher::`). `JobRun.matchers` is the job-wide list (shared with forks); `exec_with` feeds each output line to a per-step copy and logs matches as annotations.
- **`context.rs`**: `RepoInfo::detect` shells out to `git` to fill the `github` context (repo slug from `--remote-name`, sha, ref, default branch); `host` (`--github-instance`) drives the server/API URLs. `event_ref_and_sha` then overrides ref/sha from the event payload the way GitHub does (`refs/pull/N/merge`, release tags, push `ref`/`after`, …), and `GITHUB_*_URL` from the caller's environment win.
- **`history.rs`**: `Recorder` (in `Config.history`, unless `--no-history` or `--insecure-secrets`) writes each run to `<cache>/runs/<id>/`: `meta.json` from `main.rs` (masked argv, repo, event, jobs by stage, and `config`: env/vars/inputs masked, secret names, platforms), every `Logger::line` after masking into `log.jsonl`, and `result.json` at the end. `Summary` / `Job::feed` rebuild jobs and steps from the log's status lines (`⭐`, `✅`/`❌`/`⚠️`/`🛑`, `⏭️`, `🚀`/`🏁`, `ℹ️` notes on what a local run does not reproduce) and keeps step summaries recorded beside them, formatted and parsed by `markers.rs`, whose tests check each line parses back.
- **`dashboard.rs`**: `--dashboard` serves `dashboard.html` (one self-contained page, no build step) and a JSON API (`/api/runs`, `/api/runs/<id>`, `/api/runs/<id>/job?workflow=&job=`) through `servers::serve`.
- **`servers.rs`**: std-only HTTP/1.1 servers jobs reach through `ACTIONS_CACHE_URL` (`@actions/cache` v1 API, on by default, entries persisted in `index.json`) and `ACTIONS_RESULTS_URL` (`@actions/artifact` v2 Twirp API plus Azure-blob-style block uploads, with `--artifact-server-path`; the toolkit sends proto field names such as `workflow_run_backend_id`) plus `ACTIONS_RUNTIME_URL` (the v1 API of the v3 actions, files under `v3/<run>/`, gzipped chunks stored with a `.gz__` suffix). `ACTIONS_RUNTIME_TOKEN` is a JWT signed with a per-run key (`RuntimeAuth`, or the caller's own token) whose `scp` claim carries the run/job IDs the toolkit parses; the artifact API refuses calls without it, except the signed block URLs. The cache API lives under a random per-run prefix (`cache_token`), lowercases keys, and garbage-collects entries (`CacheStore::gc`) on start and after each upload. They bind `127.0.0.1`, or `0.0.0.0` for Apple containers (reached via the vmnet gateway); a failure to start the cache server only disables it.

Parity with act is measured by `scripts/act_suite.py`, which runs act's runner integration tests (`TestRunEvent`, `TestRunEventHostEnvironment` and the single-workflow tests in `pkg/runner/runner_test.go`) through runthrough; see `docs/act-parity.md`, sixth pass, for the command and the last result.

Adding a fixture-based behavior: extend `tests/fixtures/repo/.github/workflows/*.yml` (or its local actions under `.github/actions/`) and assert on the output in `tests/e2e.rs`. Each fixture workflow is keyed to its own event (`deployment`, `release`, `check_run`, `fork`, …) so tests stay independent. Tests needing local port binding, Docker or Apple `container` are `#[ignore]`d: run `cargo test --offline -- --ignored` outside the sandbox (they need local `debian:12-slim` and `pgvector/pgvector:pg16` images).
